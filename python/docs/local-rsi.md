# Local RSI reference

Local RSI keeps Tasks, traces, feedback and Recipe versions on your machine and learns Recipes with your own model.

`from cosens.local import LocalRSI, ChatCompletionsModel, CodexCLIModel`. Requires `cosens-sdk[local]`.

`LocalRSI(*, client=None, model, state_path=None)` stores state in SQLite (default `~/.cosens/local-rsi.sqlite3`). `client` is a `CoSensClient` used only for Memory recall (`/v1/memory/*`) and the Recipe store (`/recipes`), or `None`. `memory=` is a deprecated name for `client=`. Call `await rsi.aclose()` when done; it returns any running generation to the queue.

## Workflow methods

`LocalRSI` keeps its earlier in-process names for corrections and learning (`get_revision`, `start_revision`, `start_recipe_candidate`, `wait_workflow_job`, …); its task and new-execution methods follow the execution API's shapes. With those four, its workflow methods are `create_task`, `get_task`, `list_tasks`, `supplement_task_context`, `artifact`, `get_artifact`, `start_execution`, `get_execution`, `submit_execution`, `record_feedback(revision_id, ...)`, `get_recipe_candidate`, `resume_recipe_candidate`, `list_recipe_candidates`, `get_recipe_versions` and `get_task_recipe`. A failed candidate raises `RSICandidateFailed`, imported from `cosens.local.recipes`. As on the service, `start_recipe_candidate` needs feedback on the revision or an earlier one in its chain; without it, it raises `RSIFeedbackRequired` (from `cosens`) and creates no candidate, version or receipt.

`create_task`, `supplement_task_context`, `get_task`, `list_tasks` and new-execution starts take and return the same task and execution shapes as `client.atoms`; `model` is set on the model object and corrections use `start_revision`. A Task is a capability: `create_task(*, key, objective, artifacts=None, recipe=None)` keeps the objective and reference material (a bare artifact id is a `reference`) and returns `{task_id, objective, artifacts, context_version}`; `supplement_task_context(task_id, *, expected_context_version, objective=None, artifacts=None)` changes only those. Each execution carries its own input: `start_execution(task_id, *, key, source, objective=None, artifacts=None, self_contained=None, recipe_id=None, recall_memory=False)` freezes `task_context` and `input` in its request. It refuses an `external_artifact` input without a `submitted_output` with `ValueError("external_artifact requires submitted_output")`, as `client.atoms` does, and any other incomplete input with `ValueError("the execution input is incomplete: …")`, naming `objective` or `original_input_or_self_contained_task`. A start key belongs to one execution start: reusing it for another task, input or source, or for a `start_revision`, raises `ValueError("idempotency key reused with different execution")`, as `client.atoms` does. The key covers only what the caller sent, so a start resent after `supplement_task_context` returns its first receipt. A start receipt reports the execution's `kind`: `original`, `reconstructed`, or `revision` for a `start_revision`. Every execution reports its `instance_id`: its own id, or for a `start_revision` the instance of the execution it continues. `get_task` lists the executions and the task's `recipes`, each `{recipe_id, current_version, latest_version, learning}`, where `learning` (`{execution_id, version, status, phase, error}`, or `None` for an imported version) is the learning of the newest version. A Recipe belongs to one task: `recipe_id` must name one of the task's Recipes (`LookupError` otherwise, and `ValueError("Recipe has no usable version yet")` before its first version is learned), a task with several needs one named, and a learning adds its version to the Recipe the learned execution followed.

## Evidence references and the store upgrade

Its evidence references now use `execution_id`: Recipe steps, lessons and attribution cite `{execution_id, event_id}`, and the learning history names each entry's execution (and its feedback's), calls a revision execution a `correction`, and names its source execution. This matches the service and the shared `contract/local-rsi` fixture. A store written by an earlier SDK is upgraded once, in one transaction, when it is first opened. Stop older LocalRSI processes before that, and do not open an upgraded store with an earlier release: downgrading a store is not supported. If a stored Recipe or context no longer matches its hash, or names a revision the store lacks, opening raises `LocalStoreUpgradeError` (from `cosens.local`), which names the store, the candidate and the column, and nothing is changed; open the store with the previous release, or move the file aside to start a new one. A store written by a newer release raises the same error.

The same first open moves a store written before tasks became capabilities onto the new shapes, as the service's migration 015 does: each task keeps only its objective (its old artifacts were the instance input, which every request froze), each request and start receipt freezes `input` and `task_context` in place of `context` and `context_version` with its request hash unchanged, each start receipt gains its `kind`, every execution gets its `instance_id`, and each learning context becomes `workflow-recipe-context-v3`, with its history entries' `input`, a `task_context` and empty `task_materials`, and its hash recomputed, which a replayed `start_recipe_candidate` then reports. `create_task` and `start_execution` receipts keep the request hashes of their old requests, which no request now matches: reusing such an idempotency key raises `ValueError("idempotency key reused with a different request")` for `create_task` and `ValueError("idempotency key reused with different execution")` for `start_execution` (a key that started executions of two tasks keeps only its first receipt), so keep using an existing task by its `task_id` (a new `create_task` key makes a new task, without the old task's Recipes) and start executions under new keys. A store in which one Recipe serves several tasks is not upgraded: opening raises `LocalStoreUpgradeError` naming the Recipes and their tasks, and nothing is changed. No release can unbind a Recipe from a task, so keep using such a store with the previous release, or move the file aside to start a new one.

## Other differences from `client.atoms`


- `model` and `max_completion_tokens` are set on the model object, not per call.
- Each new current version is uploaded to the Recipe store with `upload_recipe`, without evidence references, under the chain's `recipe_id`. `previous_version` is the last version the store is known to have, so a version uploaded first from another machine makes the upload a `publish_conflict`; when the store is ahead with this chain's own earlier version, whose response was lost, the upload is retried on top of it. The local version stands either way, except after the service's current version is moved (`set_current_recipe_version`).
- When the service's current version moves away from the last version uploaded from here, back or forward again, the chain follows the service: its current version becomes the local version with that number when that version is known to be the service's copy (uploaded from here, or holding the same Recipe), or, when this machine has no version with that number, the service's, imported on the local copy of the version it builds on; later versions are numbered above every version the service stores. A local version with that number that holds another Recipe and was never uploaded was numbered here before another machine uploaded the number; the service's copy cannot be stored beside it, so the chain does not follow and uploads stay `publish_conflict`. `start_recipe_candidate` checks this before learning, and the same step fails each finished local version that the new current version does not lead to and that was not uploaded, with `previous_version_changed` (candidates queued behind it fail with `previous_version_failed`). When the check cannot read the service, or the service moves after it, the upload finds the move instead: when the service's current version is below the last version uploaded from here, or is a local version known to be the service's copy that the candidate does not build on, the candidate fails with `previous_version_changed` without being uploaded. An upload reply that arrives after another learning followed such a move changes nothing: the candidate stays failed, and the last version known to be uploaded stays the one that learning followed. `resume_recipe_candidate` rebuilds a failed candidate on the current version. `get_recipe_versions` marks `rolled_back` on each finished version that the current version does not lead to.
- `search_recipes(query, limit=10)`, `list_recipes(limit=20, cursor=None, origin=None)` and `get_recipe(recipe_id, version=None)` read the Recipe store, as on `client.atoms`.
- `create_task(..., recipe=view)` takes a Recipe returned by `get_recipe`. An `uploaded` Recipe continues under its own `recipe_id`: the next local version is its version plus one and is uploaded on top of it; if the chain is already on this machine, start an execution of the task that owns it, with its `recipe_id`. A `generated` Recipe starts a new local chain at version 1 without its evidence references. Anything that does not match `contract/local-rsi/recipe-upload.schema.json` is rejected.
- `publish_recipe(recipe_id)` retries uploading the current version. When the upload finds that the service moved its current version off that version's base, the chain follows the service and `publish_recipe` raises `RSICandidateFailed` with `previous_version_changed`, as `wait_workflow_job` does; the version is not uploaded, and `resume_recipe_candidate` rebuilds it on the current version.
- `wait_workflow_job` runs the generation. A candidate nobody waits on is not generated.
- A `wait_workflow_job` timeout leaves the generation running in this process; wait on the same ID to continue.
- Candidates do not report `memory_usable`, `memory_validation` or `max_completion_tokens`, and candidate lists do not report `user_id`.
- Recipe candidates also report `publish_state`: `pending`, `published`, `failed` or `publish_conflict` (`None` without a client, and for a version started from a generated Recipe).

## Models

`ChatCompletionsModel(client, model, *, max_completion_tokens=32000, timeout=300, extra_body=None)` takes your `AsyncOpenAI` client.

`CodexCLIModel(*, model=None, reasoning_effort="medium", timeout=300, executable="codex")` runs your installed Codex CLI and uses its logged-in quota (Linux and macOS). Each call is isolated from your Codex hooks, MCP servers and working directory.

Local RSI does not re-check whether Memory cited by a Recipe has since changed.
